# 静止玩家攻击问题：诊断版使用方法

此版本用于收集尚未定位的攻击异常，**不表示已经修复攻击问题**。它包含 `.4` 的带方括号账号名传送修复，保留现有账号名、UUID、存档和伤害规则。

## 开启一次复现

1. 停服，将旧 EasyAuth jar 替换为 `easyauth-fabric-mc1.20.4-4.0.0-multisource.5-diagnostic.jar`；不要同时放置两个 EasyAuth jar。
2. 在现有服务器 Java 启动命令中，`-jar` **之前**加入 `-Deasyauth.debugCombat=true`，保留已有的其他 JVM 参数。例如：

   ```text
   java -Deasyauth.debugCombat=true -jar fabric-server-launch.jar nogui
   ```

3. 将正版和 MUA 客户端放在两个独立游戏目录运行，避免继续共写日志和 Bobby 缓存。先保持其他模组配置一致；本次不需要清空账号或服务器世界。
4. 两名玩家都处于生存模式并站在彼此攻击距离内，确认一次正常攻击可以生成 `[combat-debug]`。随后让 MUA 静止，间隔约 1 秒攻击数次；再让 MUA 移动一次后继续。记录大致时间，以及 MUA 端实际血量是否下降，而不只观察攻击动画。
5. 保留此次服务器 `logs/latest.log` 和两个客户端各自的 `logs/latest.log`。复现后移除该 JVM 参数并重启，即关闭诊断。

默认不开启诊断，不需要改 EasyAuth 的密码日志或全局 `debug` 配置。每次服务器进程最多输出 1000 条战斗记录和一条触顶提示；达到上限后需重启才能继续采集。不要对着目标持续高速连点，少量对照即可。

## 如何区分问题发生的位置

- `stage=attack`：攻击包到达服务器主线程的观察点，包括攻击者、目标、双方服务器坐标及距离、目标 tick、受伤冷却、游戏模式和认证状态。`target=missing` 表示服务器在该世界找不到这个包指向的实体。
- `stage=hurt`：玩家之间的攻击进入目标伤害方法，记录方法返回的 `accepted` 和前后血量/冷却。`accepted=false` 不是固定原因名称，需要结合状态判断；`accepted=true` 也应查看血量等字段，不能单凭返回值推断客户端显示。
- 出现攻击记录但没有伤害记录，应调查原版距离/边界检查、其他模组的拦截等路径。日志不会将这些情况自动判定成某一种根因。
- 只有在开关确实启用、正常对照能生成日志且未触顶时，缺失记录才有诊断意义。其他模组若在观察点之前取消处理，也可能没有记录，不能仅凭缺失就断言客户端没发送包。
- 若世界时间持续推进而目标 tick 和冷却不变，可继续调查实体更新调度；若服务器确实扣血而客户端表现不一致，应调查同步或客户端显示。需要用连续记录建立证据，不能只看一次截图或一条记录。

记录不包含 IP、密码、访问令牌或纹理签名。它会包含玩家名字、UUID、实体 ID 和服务器位置，便于将两端记录对应起来。
